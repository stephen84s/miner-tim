# NET-03 — Pair share submissions to pool responses by JSON-RPC id (#17)

**Status:** Completed

Every request already carried a JSON-RPC id and it was thrown away, so a pool reply could not be paired with its submission. On a live run three replies arrived in one second with ≥2 submissions outstanding; which one was rejected was unknowable. The problem was latent: any reply with an `id` and no `method` was counted as a share reply, including keepalives — an error keepalive was miscounted as **rejected share**. Fixed by recording outstanding submissions in `pending_shares` keyed by rpc id; submit/accept/reject logs now name `rpc_id`, `job_id`, `nonce` (and latency on accept). Only pending ids count as shares; replies with unrecognised status count as rejected (logged `warn`). Unmatched replies log at `warn` except `KEEPALIVED`, which stays `debug`. Shares outstanding when a connection is replaced are drained and counted **lost** (`lost_shares`), at both reconnect paths. Stats show `(lost:N)` and `(pending:N)` when non-zero; final line always shows both. **Three review rounds; rounds 1 and 2 returned NOT MERGEABLE — each found a defect in the previous round's fix.** Round 1 found a write-then-register race that discarded accepts uncounted. Round 2 found the reorder trades that race for a differently-shaped one where a reconnect lands between insert and write, causing a share to be falsely counted lost and its stale request written to the new connection. Round 3 (Opus, raised because the fix became a locking design) found the design sound and returned MERGEABLE with three minors, all fixed: stale round-2 comment deleted, comment overclaim corrected, deterministic ordering test added. **Verification:** 171 lib + 20 bin tests pass; clippy clean. **Ledger:** `REVIEW_PR36.md`, rounds 1–3; retrieve with `git show 346a318:REVIEW_PR36.md`.
