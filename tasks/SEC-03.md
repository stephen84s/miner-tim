# SEC-03 — Stratum receive buffer bounded (#21).

**Status:** Completed

`receiver_loop` appended every read to `pending` and drained only on a newline, with no ceiling — a peer sending an endless newline-free stream grew it until the process died. No wrong hashes, no error, no log. The asymmetry is the defect: `read_line` has always capped at 1 MiB; the long-lived path a hostile peer actually reaches never did. One `MAX_LINE_BYTES` now serves both. The check is on the buffer **after draining complete lines**, so messages split across reads keep working. **Testing it took two attempts and the first was worthless**: the socket-level wiring test passed against the unbounded implementation, because the server dropped the flooding socket and the miner reconnected on EOF — a second accept for a reason unrelated to the bound. Holding the socket open makes it discriminate. Same shape as PR #22's three failed attempts, hit independently one PR later. Nine tests (159 lib + 18 bin post-rebase); four helper mutations, the wiring mutation and the `pending.clear()` mutation all caught — the last taking **three attempts**, the first two passing against the defect. Review predicted the missing clear would cause an infinite reconnect loop; **it does not** — the next newline drains the stale flood as one bogus line, and what is actually lost is the *first real job after the flood*, swallowed. Round 2 found the *first* cap for that was itself derived from the limit it guards, so it scaled with the mutation and the test passed instead of failing — recorded here as fixed when it was not. Now an absolute 4 MiB, and the figure recording that was wrong too: measured in release, one test, the threshold is **4x** (2x still passes; 4x/16x/1024x fail in 0.66 s) — the withdrawn "42 s" was a whole-suite number quoted against a single-test one. **Round 3 found two more majors**: `e3b339f` swept 25 files / 5.7 MB of `mutants.out/` scratch into a public repo via `git add -A`, absent from the very Files-changed list it was editing (now untracked and ignored); and the rebase added a *second* SEC-03 row beside the stale pre-round-1 one, with blank lines that terminate the GFM table — confirmed against GitHub's renderer, which dropped FIX-01, both SEC-03 rows and `Pending` out of the table. DOC-02 round 3 recurring in the same file. 159 lib + 18 bin, clippy clean. Not established: no hostile *pool* end to end, and the 1 MiB value is inherited from `read_line`, not derived from a survey of real message sizes.
